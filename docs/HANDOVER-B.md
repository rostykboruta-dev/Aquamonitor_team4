## Тиждень 1
**Date:** 2026-10-18
**Author:** Антоняк Констянтин

## 1. Зроблено
* Закрито перший пункт переліку ролі B: «Клієнт зовнішнього джерела: HTTP-запит, розбір JSON, перетворення у структури ролі A».
* `src/aquamonitor/dataio.py`: `ParseError(HydroError)`, `build_usgs_url`, `fetch_usgs_json`, `parse_usgs_json`.
* `fetch_usgs_json(site, parameter, period)` робить GET-запит до USGS Water Data API через `urllib`; помилки мережі й тайм-аут стають `ParseError`.
* `parse_usgs_json(json_str)` перетворює відповідь API (GeoJSON, поле `features`) у `list[Observation]`: час у UTC, `null` стає `None`, результат відсортовано за `(sensor_id, час)`.
* Перевірено живий запит (пост 01646500, параметр 00065, 6 годин): отримано 68 записів. USGS Water Data API доступний.
* 11 тестів у `tests/test_dataio.py` (усі зелені), мережу не використовують. На помилкові дані: порожній рядок, не JSON, немає `features`, немає `time`, поганий час, нечислове значення, не рядок на вході, збій мережі. Зразок реальної відповіді: `tests/data/usgs_sample.json`.

## 2. Не зроблено
* Парсер журналів регулярними виразами, очищення даних, генератор `stream_observations`, менеджер `ArchiveReader`, генератор синтетичних даних, експорт у CSV/JSON (наступні пункти переліку).
* Формат RDB не підтримується: завдання вимагає «JSON/RDB», ми взяли JSON, бо старий сервіс USGS виводиться з експлуатації.
* NOAA NCEI і Kaggle не перевірялися.

## 3. Ухвалені рішення
* Використано новий USGS Water Data API (`api.waterdata.usgs.gov/ogcapi/v1`), а не старий `waterservices.usgs.gov`.
* `sensor_id` має вигляд `<пост>-<параметр>`, наприклад `USGS-01646500-00065`.
* Час без зсуву вважається UTC; усі `Observation` повертаються з часом UTC.
* `ParseError` використовується і для помилок читання (мережа), і для помилок розбору, як сказано в `spec.md`.

## 4. Проблеми
* `Observation` не має поля для статусу даних (`Provisional`/`Approved`), тому API-шний статус не зберігається. Потрібне рішення ролі A.
* `fetch_usgs_json` читає лише першу сторінку (до 10 000 записів). Тиждень 15-хвилинних даних це близько 700, але місяць уже не вміститься.
* Якщо в відповіді кілька параметрів, функція повертає їх разом; `Series` приймає лише один `sensor_id`, тому треба відфільтрувати за `sensor_id`.
* `parse_usgs_json` і `fetch_usgs_json` треба додати в `docs/spec.md` (сигнатури, формат `sensor_id`).

## 5. Далі
* Парсер текстових журналів гідропоста регулярним виразом (дата, код поста, значення, прапорець якості). Формат рядка спершу зафіксувати в `docs/spec.md`.
* Очищення: виявлення викидів, уніфікація часу, журнал відкинутих записів (`clean_observations`).

## 6. Обережно
* Не змінювати сигнатури `fetch_usgs_json` і `parse_usgs_json` без запиту на злиття, який переглядають усі: від них залежить `cli.py`.
* `parse_usgs_json` повертає всі сенсори разом; перед створенням `Series` відфільтруйте один `sensor_id`.

## 7. Як запустити
1. Переконайтеся, що ви в корені репозиторію й активовано віртуальне середовище.
2. Запуск тестів:
   ```powershell
   $env:PYTHONPATH="src"
   python -m unittest tests.test_dataio -v
   ```
3. Приклад використання:
   ```python
   from aquamonitor.dataio import fetch_usgs_json, parse_usgs_json
   observations = parse_usgs_json(fetch_usgs_json("01646500", "00065", "PT6H"))
   ```

## 1. Зроблено
* `fetch_usgs_json` читає всі сторінки за `rel="next"` (захист від циклу і `MAX_PAGES`).
* `parse_usgs_json`: відхиляє `bool`, `NaN`, `inf`; рівень з USGS перераховано з футів у метри через `convert_units`; `status` заповнюється з `approval_status`.
* `parse_log_line` (формат у spec, розділ 2): прапорець A/P/E стає статусом.
* `clean_observations`: UTC, дублікати, діапазон у метрах.
* Нові тести для всього вище, розділ dataio у spec.

## 2. Рефакторинг
* З `fetch_usgs_json` винесено `_read_url`, щоб читати кілька сторінок тим самим кодом. Сигнатура не змінилась.

## 3. Не зроблено
* Статистичні викиди (наприклад, за ковзною медіаною) у `clean_observations`: зараз лише діапазон.
* `stream_observations`, `ArchiveReader`, генератор синтетичних даних, експорт CSV/JSON.

## 4. Проблеми
* Одиниці значень у журналі не вказані, припущено метри. Діапазон `clean_observations` для метрів -3..30, для інших величин його треба задавати окремо.
* `MAX_PAGES = 100`: для дуже довгих періодів сторінок може не вистачити.

## 5. Далі
* Статистичні викиди.

## 1. Зроблено
* Дороблено пункт 3 (очищення): `clean_observations` тепер ще й шукає статистичні викиди фільтром Хампеля (`_find_spikes`). Кожен сенсор перевіряється окремо, рівномірне зростання рівня викидом не вважається, причина кожного відкинутого запису пишеться в журнал.
* Перевірено джерела з тижня 1 (01.11): NOAA NCEI Access Data Service відповідає (HTTP 200, денні опади `PRCP` у мм для станції USW00013743, аеропорт Рейгана біля Вашингтона). Kaggle: пошук і список наборів доступні (HTTP 200), але завантаження файлів потребує облікового запису й API-ключа, тому не перевірялося.
* Закрито блоки коду в записах тижня 1 у `HANDOVER-D.md` і `HANDOVER-E.md`: записи тижня 2 більше не показуються як код.
* 5 нових тестів у `tests/test_dataio.py` (усього 33), зокрема на помилкові параметри. Реальний зразок USGS не втрачає жодної точки.

## 2. Не зроблено
* Спринт 2: `stream_observations(path)`, менеджер `ArchiveReader`, генератор синтетичних даних і експорт у CSV/JSON.
* Клієнт NOAA для опадів: поки лише перевірено, що джерело доступне.

## 3. Ухвалені рішення
* Параметри фільтра: 5 сусідів з кожного боку, поріг 5 робастних σ і не менше 0.15 м (близько 0.5 ft). Поріг у метрах, бо `parse_usgs_json` уже переводить фути в метри.
* Нові параметри `clean_observations` мають значення за замовчуванням, тож старі виклики не змінюються.

## 4. Проблеми
* Справжній різкий стрибок (наприклад, скидання води з греблі) фільтр може прийняти за викид; тоді треба збільшити `min_deviation`.

## 5. Далі
* Генератор синтетичних даних (завдання вимагає його як резерв, якщо USGS недоступний), `stream_observations`, `ArchiveReader`, експорт у CSV/JSON — спринт 2.
* Клієнт NOAA (денні опади) для авторегресійної моделі ролі C у спринті 2.

## 6. Обережно
* `clean_observations` тепер може відкинути більше точок, ніж на тижні 2: причини дивіться в журналі відкинутих записів (`aquamonitor.log`).
